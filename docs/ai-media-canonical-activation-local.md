## 身份和授权边界

- 老用户 `activations.bound_machine_code=v2_*` 不迁移。现有设备会话与凭证校验不变。
- 已联网且通过原设备凭证验证的老设备，在硬件采集完成后，后台向
  `POST /api/license/identity/baseline` 登记一次因子哈希基线。登记前须在本进程重新采集，
  不以可能被系统镜像复制的本地因子缓存建基线。它不修改授权行、有效期或凭证。
- 新机首次激活强制重新采集因子，最多等待 8 秒；不信任镜像里复制的 7 天身份缓存。
  无可用因子时走原有人工核对，不提前替换本地 active v2 码。
- 只有**合法未使用的时间卡**、原 v2 主授权有已认证基线、两项独立强因子确实冲突，
  且安全存储中的安装恢复密钥已持久化，才可进入独立绑定。
  Windows 的 MachineGuid 差异本身不计入这两项；典型证据为 BIOS UUID 和系统盘序列号均不同。
  相同或不确定时拒绝自动消耗第二张卡。已绑定旧卡始终先受旧设备凭证规则保护。
- 服务端生成随机 `v3_*` canonical，并与新卡授权行、因子哈希、恢复密钥散列**同一事务**写入。
  不采用客户端 candidate 作为绑定码；既有 `(app_name,bound_machine_code)` 唯一索引和
  `activations` 表结构不变。新增映射/基线表均有 `app_name='ai-media-library'` CHECK 限定。
- 安装恢复密钥先由 Electron `safeStorage` 加密落盘，再发起激活。它是响应丢失、
  安全存储写凭证失败、重试或程序重启后的持有证明；服务器只存其散列，
  并从密钥、code_id 和 canonical 稳定派生同一设备凭证，避免重试撤销第一次成功响应。
  **它不是硬件真实性证明**，不同密钥或 candidate 本身都不能判为不同设备。
- 仅在身份诊断中见过的 canonical 不构成授权依据；客户端只接受已写入设备凭证的
  服务端签发码，或带完整设备凭证的首次成功激活响应。
- 已签发 canonical 的状态检查、会话刷新、解绑和明确确认的现有时间续期接口仍按服务端
  `activations.bound_machine_code` 运作。客户端将 canonical 作为安全存储中的有效绑定值，
  但 v2 采集算法和旧卡绑定均不变。离线宽限签名绑定 canonical；网络失败时对 canonical
  再做新鲜强因子采集，镜像复制的凭证/离线缓存不能仅凭相同 v2 离线放行；网卡等弱因子
  变化不改变离线匹配摘要。
- 对原卡无基线、强因子不足/冲突不明确、恢复密钥遗失或因子变化的情况，不自动接管或
  迁移已有卡；提示人工核对。老设备正常联网授权不因异步基线登记失败被阻断。

## 开关与兼容回退

`AIML_CANONICAL_CREATE_ENABLED=true` **仅控制创建新 canonical 绑定，默认关闭**。
`AIML_IDENTITY_PHASE` 继续只控制原 4b 观测，保持 `off`；两者不能混为一谈。
关闭创建开关后，已有 canonical 仍可重试、校验、解绑、续期和离线使用。

一旦签发 canonical，**不能**仅恢复旧 4b 服务文件或设置 `phase=off`：旧文件不知道
映射/恢复流程；也不能把两个绑定写回同一个 v2 唯一键。安全停写方式是保留本候选的
兼容读取/恢复代码，把创建开关改为 false。需要完全回退代码时，必须先按已签发数量
逐一协调迁移/撤销和数据备份，不允许直接覆盖服务文件或删除映射表。
