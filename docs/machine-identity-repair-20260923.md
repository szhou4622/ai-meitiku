# 全新激活码的设备识别修复

2026-09-24，按实际反馈调整为纯客户端身份修复：不要求授权服务器新增接口。

## 适用场景与界面

用户确认输入全新、从未绑定的月卡或年卡；本地残留旧机器码，普通激活因旧身份冲突返回 409。

激活页新增「修复设备识别」，使用输入框中的激活码。说明保留已确认的文案：

> 重新检测本机设备信息，处理旧机器码冲突。已有授权将先核验，再决定是否迁移。

下方进一步明确本版范围：只处理全新未绑定卡；如果发现历史凭证或离线授权，停止此流程并保留原数据，由原授权验证或管理员迁移处理。本版不提供已有授权自动迁移。

用户输入新码后点击修复。若中断，按钮变为「继续修复设备识别」，普通激活暂时禁用；重新启动后输入同一张码继续。服务器明确拒绝首次请求时允许纠正输入；一旦有不确定的请求结果，不允许换卡重试。

## 客户端行为

- 重新读取系统 UUID，沿用新的 `system_uuid_v1` 派生规则；Windows 使用 `Win32_ComputerSystemProduct.UUID`，不再沿用旧 MachineGuid 机器码。
- 新身份在隔离存储中生成，同时重新采集强硬件因子。未读到有效 UUID 或强因子不足时，不请求激活。
- 检查本地完整或残缺授权凭证、历史离线凭证；存在即停止新身份修复。正常授权、过期续期等原流程继续保留。
- 使用系统 safeStorage 加密写入 `license-identity-repair.v1.bin`，保存原身份/机器码备份、新身份、输入的新激活码、恢复证明和执行阶段。文件不交给渲染进程，日志不记录完整码或证明。
- 隔离的授权服务使用新机器码调用线上已有的 `/api/license/activate`。只有服务器确认新激活码成功并返回完整凭证后，才写入新身份、机器码缓存、恢复证明和凭证。没有本地清空授权的操作，也不修改旧激活码的服务端绑定。
- `prepared → accepted → committed`：已收到凭证但本地写入中断时，下次启动重放本地写入，不再次激活。请求结果不确定时保留相同新码及候选身份，禁止直接换另一张新码继续。修复完成后清除内存中的旧身份缓存，并重新读取因子。
- 已使用新身份的安装不再重复换码。无法唯一识别的硬件、克隆 UUID、已有新身份授权等情况仍需核对，不随机生成新码绕过冲突。

关键文件：`electron/machine-identity-repair.mjs`、`electron/license-secure-store.mjs`、`electron/machine-code.mjs`、`electron/license-service.mjs`、`electron/main.mjs`、`electron/preload.cjs`、`app/page.tsx`。

## 与服务器的关系

新机器码完全由客户端根据系统 UUID 生成。修复按钮不要求服务器迁移、解绑或删除旧机器码，也不需要新增路由。

服务器仍然参与普通的在线激活：校验用户输入的全新月卡或年卡，并把它绑定到客户端提交的新机器码。这会创建新激活码自己的绑定记录，但不会修改旧激活码原有的绑定记录和到期时间。

客户端在服务器返回成功前只暂存候选身份；激活失败时继续使用旧身份。若请求可能已到达服务器但成功响应丢失，现有 `/activate` 无法在缺少设备凭证时自动取回第一次生成的随机凭证，客户端会保留同一张码和修复进度，避免用户误用第二张新码；这种极端情况仍需要管理员核对或重置该新码。
