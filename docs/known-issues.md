# 已知问题与后续决策记录

## Windows 系统镜像克隆导致机器码重复

### 事件背景

截至 2026-09-16，AI媒体库已经确认发生过 2 例因机器码重复而导致的激活失败：

- 截图案例 1 例；
- 本次排查确认案例 1 例。

两个事件均涉及 Windows 电脑。当前客户端 v2 机器码以 Windows
`MachineGuid` 为主要系统身份来源。通过系统镜像批量安装或克隆系统时，镜像中的
`MachineGuid` 可能被原样复制到另一台物理电脑，导致两台电脑生成相同的 v2
机器码。授权服务器随后无法仅凭该机器码可靠地区分两台设备，从而出现激活失败或绑定冲突。

### 当前处置

目前由客服核对用户、激活码和设备情况后，在授权后台手工解绑，再让用户使用原激活码重新绑定。
该处置不要求用户重新购买授权，也不得通过修改注册表 `MachineGuid` 或其他系统标识来解决。

### 已设计但暂缓上线的方案

v3 多因子硬件指纹方案已经完成设计，目标是组合多个经过归一化和单向哈希的硬件因子，降低系统镜像克隆造成的撞码风险，同时保留 v2 老用户迁移能力。

第 3 批计划仅保存 v3 采集模块与单元测试，作为不接入运行时的代码储备；在正式启用前，不修改现有 `machine-code.mjs` v2 路径，不改变客户端或服务器的绑定行为。

### 后续启用条件

先完成第 2 批授权错误结构化日志，仅针对 `app_name = 'ai-media-library'` 收集脱敏的错误类型、机器码前缀、客户端版本和来源网段。日志运行约 3 个月后，根据机器码冲突的实际发生频次、影响用户数量和客服处理成本，重新评估是否启用 v3。

启用 v3 前仍须满足以下边界：

- 不得以硬件因子匹配替代或绕过现有 `device_credential` 校验；
- 不得影响共用授权服务器的其他软件；
- 必须保留策略开关、v2 降级路径和隔离性回归测试；
- 不上传或记录任何原始硬件序列号。

## 畸形激活请求的应用归属限制

授权服务器的 `/api/license/activate` 是多个软件共用的入口。请求体只有在 JSON
完整解析成功后，才能可信读取顶层 `app_name`。如果正文被截断、编码错误或 JSON
结构损坏，即使残缺文本中看起来包含 `app_name`，也不会扫描或猜测其所属软件。

这类无法可靠归属的解析失败统一写入独立的
`/var/log/ai-media-license/unattributed-errors.jsonl`，只记录时间戳、脱敏 IP 网段、
请求体声明长度和去参数后的 Content-Type。不会记录请求正文、完整 IP、激活码、
机器码或设备凭证。

已知限制是：原本来自 `ai-media-library` 的畸形请求也可能只能出现在未归属日志中，
不能进入目标应用的 `activation-errors.jsonl`。这是有意采用的保守边界，用于避免在
共享入口扫描不完整请求体、误判其他软件或新增第二处共用代码改动。该限制只影响日志
归属，不改变授权校验、HTTP 状态、响应正文或数据库状态。

## 千川预览接口未纳入媒体流并发限制

提交 `17957c7` 为主进程的 `/__media/` 路径加了并发闸门
（`MAX_ACTIVE_MEDIA_STREAMS = 12`，见 `electron/main.mjs` 的 `pipeRegisteredMedia`），
用于避免大素材库同时发起大量流式请求把本地 HTTP 服务打满。

该闸门目前只覆盖 `serveRegisteredMedia`。以下两条路径仍是不受限的
`createReadStream().pipe(response)`：

- `/__qianchuan_preview/`（`serveQianchuanPreview`），单个预览上限为
  `QIANCHUAN_PREVIEW_MAX_BYTES = 2GB`；
- 主进程中直接按解析路径返回文件的静态分支。

千川预览的单文件上限远大于普通素材，理论上比 `/__media/` 更需要限流。当前未纳入，
是因为两条路径的生命周期和 token 失效策略（`QIANCHUAN_PREVIEW_TTL_MS`）与注册素材不同，
合并限流需要先确认预览被闸门排队时的超时行为，避免预览请求在队列里等到 token 过期。

该限制只影响本地流式读取的并发上限，不改变授权校验、千川绑定或任何服务端行为。
