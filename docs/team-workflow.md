# 团队协作配置

唯一仓库：`https://github.com/szhou4622/ai-meitiku`。用户已决定暂时保持公开。

## 当前阶段

当前建立的是仓库管理基线，完整应用源码与可运行基线待导入验证。
不将仓库检查通过等同于应用能启动、构建成功或生产可用。

## 合并规则

- 新任务从最新 `origin/main` 建立 `codex/<任务名>` 分支，续做使用原任务分支。
- 必须通过 PR 合入 main；合并前同步 main，解决讨论，并通过 `repository-checks`。
- main 保护适用于管理员，禁止强推与删除；不使用绕过参数合并。
- 只允许 Squash Merge；已合并的远程任务分支自动删除。
- 当前只有一位成员：PR 必需，但批准人数暂设为 0；这是单人过渡流程，没有独立复核保障。
- 第二位成员加入并接受邀请后，把批准人数改为 1；代码变化撤销旧批准，重新复核。
- 多人或多个 AI 同时工作必须使用独立目录和任务分支，不同时改同一工作目录。
- 本次没有配置生产部署。开发、PR 合并与生产发布是不同动作。

## 当前检查范围

工作流 `.github/workflows/ci.yml` 在所有面向 main 的 PR 创建、更新、重新打开以及 main 推送时运行，无路径过滤。
唯一必需检查名为 `repository-checks`，使用只读仓库权限，不访问生产服务。

检查实际执行以下内容：

1. 必需的仓库文档、模板、检查脚本存在并已纳入 Git。
2. 不跟踪真实 `.env` 文件、常见密钥/数据库文件、依赖与临时目录。
3. 单文件不超过 10 MiB；大型交付件另行安排存储。
4. 改动没有 Git 可识别的空白错误或冲突标记。

本地将本任务文件暂存后执行：

```bash
python scripts/check_repository.py
git diff --cached --check
git diff --check origin/main HEAD
```

文件名检查不能识别所有秘密。公开仓库的 GitHub secret scanning 和 push protection 保持启用，提交前仍要检查内容；这些也不能保证检出所有密钥。

## 源码导入后必须补齐

- 记录来源、版本、已有历史和导入范围，核对许可证及公开范围。
- 补齐真实安装、启动、构建、测试命令和必要的无密钥配置示例。
- 根据技术栈增加应用测试和构建检查，先验证实际运行，再加入 main 必需检查。
- 必要测试不能因条件判断而跳过；多任务 CI 应使用始终执行的最终检查，核验所有必需任务确实成功。
- 用干净环境验证可运行基线，建立版本标签；记录生产版本和数据备份策略。

## 每次交接

分别报告已开发、已提交并推送、已验证、已合并、已上线。
提供分支、提交号、PR 与检查链接，明确未完成项。
不覆盖未知改动，不修改其他仓库，不因检查失败关闭保护。
